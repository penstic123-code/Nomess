# nomess 是怎么工作的

[English](how-it-works.md)

这篇讲 nomess 的每个部分做什么、为什么这样设计、背后的原理。装法和命令见 [README](../README.zh-CN.md)。

## 它要解决的问题

让一个 AI 改代码，问题不大；让几个 AI 连着几周改同一个仓库，代码会慢慢变乱。原因很具体：每个代理只看得到眼前的任务，它不知道三天前另一个代理已经写过一个一样的工具函数，不知道存档只该经过某一个模块，也不记得上周踩过的坑。于是同一件事出现第二个入口，同一段逻辑被复制到第三个文件，修 bug 的人在症状处加个特判，而不是回到根因。

每一步单看都合理，攒起来就是屎山。返工也从这里来：一个改动和另一个系统冲突，要等合并或运行时才发现。

nomess 的思路是：把项目的规矩写下来，能机械检查的交给脚本在提交时检查，不能机械检查的交给流程和审查，过去学到的东西在合适的时候递给代理。

## 总体设计

几条贯穿全局的原则：

- **能自动检查的，不靠 AI 记住。** 提示词会被忽略、会在长对话里被压缩掉；git 钩子每次提交都会跑。所以 nomess 最硬的部分是脚本，不是文字。
- **钩子不花 token。** 所有检查都是 Python 脚本，不调用模型，提交时多等一两秒，不多花一分钱。
- **只挡新问题。** 老项目里本来就有的问题记进基线，不逼你一次还清；只有新增的和变坏的才挡提交。
- **一切都是 markdown 和 JSON。** 教训、记忆、系统图、配置都是能读、能改、能进 git 的文本文件。没有数据库，没有后台服务，不联网。
- **小项目要轻。** 一个人用一个代理的项目，只开最确定的三项检查；规模越大，打开的东西越多。

整个插件只依赖 Python 3.9 和 git，Windows、macOS、Linux 上行为一致。

## 六个部分

### ① 少写代码，动手前先查

这是一个 skill（`lean-change`），在 AI 写代码、修 bug、做设计之前加载。它给出一个"决策阶梯"：先问这件事能不能不做，再问仓库里是不是已经有现成的函数或约定，再问标准库或成熟的开源实现有没有，最后才是自己写，而且写最小又完整的那一版。拿不准的时候先查官方文档或开源实现，记下出处。

它还附带一份审查清单，审 diff 时逐条过：bug、过度设计、补丁式修法、重复和散落、耦合、越界改动、误删的校验。每条意见都要给出文件和行号，并回头重读那一行确认再报。

### ② 防屎山的流程

另一个 skill（`workflow`）在 AI 做规划、派活、合并时加载。核心是把改动按大小分三档：

- **直接改**：注释、文档、几行数据。自己改，不送审。
- **轻流程**：单点小修，一个文件、行为不变。直接派给子代理，写完审一次 diff。
- **全套**：跨系统的改动、改存档格式或对外接口。走八步：方案 → 审方案 → 试读 → 派包 → 写代码 → 交回 → 审代码 → 合并。

全套里最有意思的是"试读"。方案写好后，先交给一个便宜的模型读一遍，让它只列"读完还会问的问题"。有问题就说明方案还没把决定做完，补上再读，直到一条问题都没有才派活。这样写代码的代理拿到的是一份照做就不会错的简报，不需要自己做选择。

执行中如果发现方案和现实对不上，执行者停下交回，写清哪条前提不成立，回到方案层去改，而不是在代码里绕过去。

**提交闸门**是这一部分的硬核。`/nomess:init` 在仓库里装两个 git 原生钩子：`pre-commit` 和 `pre-merge-commit`。之所以用 git 自己的钩子，而不是 Claude Code 的工具钩子，是因为它不挑提交的人：AI 提交、人在终端提交、IDE 里点提交，都会被检查。

钩子检查的是"马上要提交的那棵树"，不是你的工作区。它先用 `git write-tree` 得到暂存区的树，在这棵树上读配置、读基线、跑检测。工作区里没暂存的草稿不影响结果，`git add -p` 只加了一半的文件，也只查加进去的那一半。主分支上提交时，系统图这类生成物会在同一次提交里自动刷新：nomess 先把刷新结果叠到候选树上一起检查，全部通过后，再把检查过的那份字节直接写进暂存区，所以检查的和提交的永远是同一份。

急用时可以 `git commit --no-verify` 跳过。但 AI 想用这招绕过闸门，会被一个 Claude Code 钩子拦下：它把命令按 shell 规则切开，认出 `--no-verify`、`-n`、改 `core.hooksPath` 这几种写法。

### ③ 系统图和自动更新的文档

nomess 从源码生成一份系统图，放在 `docs/system-map/`：有哪些子系统、谁依赖谁、哪些文件被依赖得最多。依赖关系是这样抽出来的：Python 用语法树解析 import，所以字符串和注释里的 `import` 不会被误算；其他语言用正则抽取。

设计文档里可以划出"生成段"，用两行标记围起来，里面的内容由脚本生成。主分支每次提交都会刷新这些段，文档和代码在同一个提交里保持一致。断掉的链接、过时的生成段，检查时都会报出来。

系统图是给 AI 用的"现状地图"：规划一个改动之前先看会碰到哪些子系统。人要看的是 `docs/overview.md` 这类讲意图和原理的设计文档，nomess 不替你写，但会提醒它和代码对不上的地方。

### ④ 记忆和教训

踩过的坑用 `/nomess:lesson` 记下来，先进 `docs/lessons/inbox.md`。每条教训有标题、一句话概述和正文，还可以标上它适用的路径。

隔一段时间跑一次 `/nomess:dream`，它把收件箱和记忆整理一遍：合并重复的、删掉过时的、把已经验证过的教训变成规则。它先出提案，你确认后一次做完并提交；不满意就 `git revert`。整理一次大约花 9.5 万 token，所以它是手动触发的，不会自己跑。

为什么不用向量库或知识图谱？因为这里的数据量不需要。一个项目的教训和记忆通常是几十到几百条，按目录组织、加上索引就能找到；向量检索带来的是额外的依赖、不可读的存储，以及"为什么找到了这条"说不清。markdown 文件可以直接打开改，可以进 git，可以在 code review 里看到变化。

### ⑤ 按路径加载的规则

验证过的教训会被写成 `.claude/rules/nomess/*.md`，每个文件开头写着它适用的路径。Claude Code 只在 AI 读到匹配路径的文件时才加载这条规则，所以它不常驻上下文，不白占 token。

效果是：AI 打开 `src/save/` 下的文件时，自然就看到"存档只能经过 save.py""改存档格式要同时写迁移"这类当初用教训换来的规矩。不需要在每次派活时手抄一遍。

### ⑥ 屎山特征检测

这是提交闸门里跑的内置检测，一共十来项，全是脚本，不调用 AI。

**复制粘贴（D1）。** 代码先被切成一个个词，去掉空白和注释。每连续 25 个词算一个哈希，再用 winnowing 算法挑出有代表性的指纹，这是查论文抄袭常用的方法，能保证 50 个词以上的重复一定会被发现。两个文件有一串相同的指纹，就从命中处往两边扩，找出完整的重复区间。一字不差的报红；把变量名换掉的报黄（指纹在标识符换成占位符之后算，所以改名克隆也能发现）。同一段代码出现在超过 10 个文件里，就当作样板代码，不再报。

**一件事一个入口（D4）。** 在配置里写"这件事只能在这里做"，比如存档只能经过 `save.py`。别的文件里出现对应写法就报。

**子系统之间（A1–A4 和 relations）。** 在配置里说明哪些路径属于哪个子系统，依赖图里的每条边就能对应到"哪个子系统用了哪个子系统"。然后查：子系统之间绕成环、下层依赖上层、声明独立的两个子系统之间有依赖、明确禁止的某条依赖、一份数据被多个子系统写。

**并行撞文件（C4）。** 大项目的排期表里，每个包都写了它要改的文件。两个"在做"的包有同一个文件同时匹配，就报红；只凭路径开头推断的重叠报黄。

**坏味道。** 吞掉异常（P1）用语法树看 `except` 里实际做了什么：只有 `pass`，或者抓了全部异常只打一行日志，算吞掉；清理完再抛出去不算。hack 注释（P2）、`_v2` `_old` 这类命名（P5，通常说明新旧两套写法并存）、文件和函数过长（S1、S2），都是简单的匹配和计数。

**文档。** 文档之间写了同样的内容（PL-DUP），用和复制粘贴同一套指纹去查；方案里提到的路径或系统已经不存在（PL-STALE），提示方案可能过时。

**棘轮：只许变好。** 第一次装的时候，已有的问题全部记进基线 `.nomess-baseline.json`：哪条规则、哪个文件、有几处。之后每次提交只比差异：新增的挡，变坏的挡（同一文件里多了一处，或者文件更长了），基线里有的放行。修好的问题在批末收紧时从基线里删掉，以后不许再回来。

棘轮最怕被悄悄松开，所以有两道防线。B1 守基线：提交里给基线加条目、把次数调大，会被认出来。B2 守配置：关掉一项检查、把阈值调大、删掉一条规则、改子系统的路径范围，都算放宽。这两类改动要人在 PR 上打 `nomess-loosen` 标签，CI 才放行。

检测结果按文件内容的哈希缓存，文件没改就不重算；提交时只查这次改到的文件。误报的控制靠分级：只有最确定的几种情况缺省报红挡提交，可能误判的一律只报黄。真有合理的例外，在配置里写一条带理由的 `allow`，审查时会专门看新加的例外。

## 适配不同规模的项目

灵活性分四层，从粗到细：

1. **三级规模。** `nomess.json` 的 `size` 写 `small`、`medium` 或 `large`，决定缺省开哪些检测、用哪档审查、init 建哪些文件。小项目只开复制粘贴、吞异常、过长三项，审查用最轻的一档，文档只有系统图首页。中项目加上子系统成环检测和系统图分页。大项目再加排期撞文件、文档重复和方案过时，以及总排期和归属图。规模只是缺省值，显式写了的以写的为准。
2. **按目录分松紧。** `scopes` 可以给不同目录不同的设置，比如核心目录收紧、工具目录放松、测试目录不查长度。同一个文件匹配多条时，路径写得最具体的那条优先。
3. **单项开关和阈值。** 每项检测都能单独开关、单独调颜色和阈值。
4. **自动建议升降档。** nomess 会看最近的提交历史：一段时间里有好几个分支并行合入，就建议升档；很久只有一个人在改，就建议降档。建议出现在 `nomess status` 和 VS Code 状态栏里，改不改由人决定。

## 几个设计取舍

**为什么是 git 原生钩子。** 早期版本用 Claude Code 的工具钩子拦截提交命令，但这只管得住 AI，人在终端提交就漏了；而且要猜各种 shell 写法。git 钩子由 git 自己在提交时调用，不管谁提交、用什么方式提交，都会跑。nomess 会和已有的 husky、pre-commit 框架共存，不覆盖别人的钩子，而是给出一行接入写法。

**为什么检查暂存区而不是工作区。** 提交的是暂存区。如果检查工作区，你在工作区里修好了但没暂存，检查通过，提交进去的却是没修的版本。

**为什么只挡新问题。** 要求一次修完所有存量问题，结果往往是没人敢装。棘轮让旧账留在原地，只保证不变得更糟，再慢慢收紧。

**为什么文字要短。** 常驻上下文的只有两个 skill 和两个子代理的简介，加上 `AGENTS.md` 里最多 12 行的 nomess 段，一共约 530 token。其他内容都按需加载：规划时才加载流程，打开某个目录的文件时才加载那里的规则。

**它不是安全边界。** 有人存心绕过，`--no-verify` 一下就过去了。nomess 防的是"没注意"，不是"故意"。真要把住门，就在 CI 里跑 `nomess check --ci`，它直接读两次提交的配置和基线，不依赖本地文件，放宽必须带 PR 标签。
