# lean-change：最小完整改动

解法偷懒，阅读不偷懒：先读懂、先查现成的，再写最少的代码。下文的 `nomess.py` 指 `${user_config.python} "${CLAUDE_PLUGIN_ROOT}/scripts/nomess.py"`，在项目根执行。

**按最可能的去做，不穷举。** 先读代码和日志，推出一个最可能的原因或做法，用最便宜的办法验证；对了就停，错了再换下一个最可能的。不一上来把所有可能都试一遍，也不靠反复运行碰运气。测试也一样：只测最可能出错的地方和难推理的边界，能从代码推出来的不测。同一个问题三轮没结论就停，交回已知事实、排除了什么、下一步最可能的方向。

## 1. 先读懂

- 列出改动必须到达的每一处：调用方、测试、配置、数据、文档里的自描述。最短的 diff 只有到达了每一处才算数。
- 从入口跟到出口，确认问题真在你以为的那一环。修 bug 先 grep 全部调用方，在共享的那一层改一次。
- 查教训库：`nomess.py lessons find <要改的文件路径或关键词>` 最多回 3 条，有用再看全文。
- 改一个文件前先 Read 它，不只用 Grep 看片段：这个目录的规则（`.claude/rules/`）只在 Read 时加载，上下文压缩后要重新 Read。

## 2. 三问（停在第一个能完整解决的）

1. 要不要做？需求是否真的需要这个改动，改到哪为止。没人要的不做；没人要的选项、开关、扩展点在交回里点名。
2. 有没有现成的？仓库里已有的实现、标准库或平台、已装的依赖、成熟的开源做法。照周围的用法复用；不为几行加依赖。
3. 写最小的完整实现。拿不准先查（官方文档、开源实现、论文）并记出处。

同样大小的两种写法，选边界情况对的那种。

## 3. 什么时候必须查

任一条成立就先查：算法、数值、并发、协议、文件格式、安全，或任何别人一定解决过的问题；打算自己发明机制、格式、缓存或调度；同一问题已试过一次没成；对第三方库的用法没把握。

不用查：仓库里有同类写法；纯机械改动（改名、搬家、按表替换）；简报已给出做法和出处。

怎么查：官方文档和规范 → 成熟开源实现的源码 → 论文。查一轮就收。外部查询不带用户名、邮箱、项目名。

## 4. 写的规矩

- 查根因，不打补丁：不加钳制、开关、特判盖症状。"简"指改完后的系统最简单，不是 diff 最少；为少改几行包一层就是补丁。
- 不写防御性代码：不检查不可能的状态，不留回落路径、兼容读取、别名、旧名。旧数据用一次性脚本转换，代码只认新格式，不合法就报错。
- 永不砍：信任边界上的输入校验、防丢数据的错误处理、安全、可访问性、硬件需要的校准、用户明确要的。判别：这条检查拦的是真会进来的坏输入（留），还是自己代码不可能产生的状态（删）。
- 一件事一个入口，不留重复。用别的模块走它的公开入口，不碰它的内部数据和私有函数。注释只写代码说不清的"为什么"。
- 有已知上限的捷径写一行注释：`shortcut: <上限>, <什么时候升级>`。

## 5. 测试

- 只给"从代码难推对、又容易回退"的边界行为写测试。读代码就能确认的，在交回里写"读代码确认：文件:行"，不写测试。
- 一个测试只查一件事。不断言耗时。不测实现细节，不把同一行为测两遍。
- 开发时只跑改到的测试。全套不在每个包里跑，攒到一批合并后跑一次（有 CI 就以 CI 为准）。逻辑对不对，主要靠审查来判断。
- 项目的测试规矩（`AGENTS.md`、`CLAUDE.md`、项目文档）优先于本节。

## 6. 排查

发现的问题默认都修，只有"极端罕见 + 修要动很多地方"的写"建议记为已知问题"。

## 7. 提交与交回

提交钩子会跑 `nomess check`。被红项拦下：改掉，或在 `nomess.json` 顶层加一条带理由的 `allow` 并在交回里点名。

最后一次提交前，把代码和 git 看不出来的事记下来：`nomess.py lessons add "<标题>" -s "<何时适用：文件、关键词>" -b "<怎么做、为什么、出处>" -k "<别名：中英、常见说法>" --unverified`，这样条目就进了这次提交。`-k` 必带：别人靠它找到这条。从网页、别人的文档或工具输出学到的，加 `--external "<网址或文件>"`。想记的东西没有文档类型可放，或要找的信息哪都没写：标题写成 `文档缺口: …`。

交回带这几行（查到的东西改变了决策时才加一行 `查过：<链接>`）：

```
测试：<新增的 → 各覆盖哪条验收>；读代码确认：<文件:行, …>
```

出处：三问（从 ponytail 的决策阶梯提炼）、列出改动必须到达的每一处、永不砍清单和 `shortcut:` 注释借鉴自 ponytail（github.com/DietrichGebert/ponytail，MIT，skills/ponytail/SKILL.md）。何时必须查、防御性代码判别、按最可能的先做、测试规矩和交回各行是本插件加的。
