# workflow：改动怎么走流程

下文的 `nomess.py` 指 `${user_config.python} "${CLAUDE_PLUGIN_ROOT}/scripts/nomess.py"`，在项目根执行；配套文件 `brief-template.md` 和 `merge-steps.md` 也用这个简写。项目大小是 `nomess.json` 里的 `size`（`small` / `medium` / `large`）；它只决定全套这一档带哪些额外步骤（第 2 节），以及检查和审查级别的缺省值。

## 1. 三档

| 档 | 什么改动 | 流程 |
|---|---|---|
| 全套 | 跨系统；改文件或存档格式；改接口；改执行时机或数据主人 | 方案 → 审方案 → 试读 → 派包 → 写代码 → 交回 → 审代码 → 合入 |
| 轻流程 | 单点小修 | 直接派包，审一次代码 |
| 直接改 | 注释、文档 | 自己改，不送审 |

拿不准往上算一档。读写了别的系统拥有的数据或时点就算全套。

## 2. 全套

1. 写方案前先看现状：谁写、谁读、在哪个时点、共享数据谁存盘；看 `docs/system-map/index.md` 上的热点清单。定好每份数据的唯一主人。
2. 写方案（第 3 节）。3. 审方案：另派一个只拿方案和归属记录的新子代理查冲突。4. 写简报并试读（第 4 节）。5. 派包。6. 写代码并交回（第 5 节）。7. 审代码（第 7 节）。8. 按 `merge-steps.md` 合入。

按大小的额外步骤：

| `size` | 额外 |
|---|---|
| `small` | 没有：方案是对话里的几行；审方案可以是用户看一眼；主人写进 `docs/systems/` 页的 `## 细节` |
| `medium` | 主人同 small。方案是 `docs/plans/` 里的一个文件；它的包列在方案的 `## 分包` 下；包并行跑之前，对着这张表手工查它们的文件有没有重叠（没有脚本查这个） |
| `large` | 还要：`docs/schedule.md` 是唯一的施工入口（包、顺序、文件、状态只写在那里；C4 在提交时查文件重叠）；派包前先在 `docs/ownership-map.md` 里定好主人 |

执行中发现方案错了，回到方案层处理（第 6 节），不绕着打补丁。

## 3. 方案

从 `${CLAUDE_PLUGIN_ROOT}/skills/init/templates/<lang>/plan.md` 拷（`lang` 取自 `nomess.json`）。

- 做完所有决定：便宜的模型读完方案和简报不用问就能开工。执行者自己拿主意是打补丁的起点。
- 只给一个主方案，不写"可以 A 或 B"；每个取舍一行理由；要有一节"没选什么、为什么"（这就是决策记录）。
- **方案头**写在最前面：`状态:`（提案 / 已采纳 / 已否决 / 已被取代）、`日期:`，可选 `系统:`（取自 `systems` 的名字）、`取代:`、`被取代:`（写了它，状态必须是已被取代）。字段名跟着 `lang` 走。
- **归档**：做完、被否决、被取代的方案挪进 `docs/plans/archive/YYYY-MM-DD-<name>.md`，不删；做完的改为已采纳。不用连续编号：并行的代理会抢同一个号。

## 4. 简报与试读

按 `brief-template.md` 的七段写，缺一段不派。只抄方案里这个包的部分；每个文件:行都亲自核对，并注明提交；给可验证的验收条件，分成**测试**（从代码难推对、又容易回退的边界行为）和**读代码确认**。

**派包前试读**：把方案路径（small：方案正文）和简报交给 `nomess:trial-reader` 子代理；它只列读完还会问的问题。把答案补进方案或简报，再试读；回"无"才派。

**并行**：一个包一个代理；文件、时点、主人、事件都不重叠才并行。一个工作树只有一个提交者：每个并行代理在自己的 git worktree 里干，协调者一次一个合入主分支。写代码的代理不改共享文档：文档句子写在交回里。

## 5. 交回

八行，缺行退回：提交号；check 结果一行；前提不成立（没有写"无"）；简报外改动（没有写"无"）；推出来没实测的前提；阶梯行；测试（加了哪些、各覆盖哪条验收；哪些条目是读代码确认的，写 `文件:行`）；教训（最后一次提交前用 `lessons add --unverified` 记下并随那次提交带上的条目标题；没有写"无"）。

## 6. 计划返修

触发：简报和现实对不上；审查发现设计漏洞；测试或评测和方案前提矛盾。

- 执行者：停下，照常交回，写清哪条前提不成立、看到了什么；绝不自己改方案或绕过去。
- 协调者：叫停受影响的包并标`返修中`（large：在总排期里；medium：在方案的分包里）；前提写在哪就在哪改（方案、总排期或归属图），不改抄本；在方案末尾加 `变更记录：<日期>，<改了什么>，<为什么>`；简报改好后改回`待派`。被叫停的包的提交不合入。
- small 没有包：改方案，重做。改得小（不影响别的包）：改方案和简报，试读改动的部分，重新派。改得大（数据主人、接口、别的包，或拿不准）：重新审方案；已合入且依赖这条前提的包，加一个返工包。

## 7. 审查

照 `${CLAUDE_PLUGIN_ROOT}/skills/review/SKILL.md` 做（Read 它；`/nomess:review` 是给用户用的）。一次改动的审查级别就是 `nomess.py review-input <base>` 的第一行（基点：和主分支的合并基点）：改动文件里最严的那一级。

- **每个级别都要审**：简报以外的改动（哪怕一行）；全套改动的每个包；任何新加 `allow` 的提交。
- 每条意见重读代码，写"采纳"或"不采纳 + 理由"。
- 逻辑对不对，主要靠审查判断，不靠测试。开发中只跑你碰过的测试；完整测试在交回前跑一次。

## 8. 提交闸门与规则

git 钩子（`pre-commit`、`pre-merge-commit`）对要提交的内容跑 `nomess check`，在主分支上还会把生成文件刷新进同一个提交。

- 被红项拦下：改掉，或在顶层加一条带 `reason` 的 `allow`（一定会被审）。绝不用 `--no-verify`，绝不碰 `core.hooksPath`。
- 能机械判断的规则登记进 `nomess.json` 的 `check.rules`，不写文字提醒：`forbid`（某写法只许出现在 `allow` 列出的文件里）、`require`（文件必须有某个头）、`cmd`（项目自己的检查）。子系统之间的约束写进 `arch`。两份必须一致的东西做成 docgen 生成段。
- 红是确定性错误，挡提交；黄是启发式，只提示。新踩一次坑，先问能不能变成一条规则；要判断的，由 `/nomess:dream` 升成路径规则。

## 9. 大小

`nomess.py status` 在信号过线时（并行分支、两边都改了的文件、教训堆积、子系统数；`status --suggest` 会列出）会打印大小建议。由人决定：升档就重跑 `/nomess:init`；降档是放宽，要走人自己的放宽流程（用 `--no-verify` 提交，PR 打上 `nomess-loosen` 标签）。

## 10. 代理

一个代理一件事，做完就结束；里程碑之间换新代理，给一页交接。同一问题三轮没结论就交回。被权限拦下的不绕过、不托人代做。git 只 add 自己的文件，不用 `commit -a`，不 push。
