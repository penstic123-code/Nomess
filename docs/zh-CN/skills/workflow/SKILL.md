# workflow：改动怎么走流程

项目规矩优先：项目的 `AGENTS.md` 或 `CLAUDE.md` 对这里任何一步另有规定（某档走几步、要不要试读、测试、审查），按项目的来。

下文的 `nomess.py` 指 `${user_config.python} "${CLAUDE_PLUGIN_ROOT}/scripts/nomess.py"`，在项目根执行（`brief-template.md` 和 `merge-steps.md` 也用这个简写）。`size`（`small` / `medium` / `large`）和 `docs_root`（缺省 `docs`，下文写作 `<docs_root>`）取自 `nomess.json`。下文的文档位置（`<docs_root>/plans/`、`<docs_root>/schedule.md`、`<docs_root>/ownership-map.md`、`<docs_root>/systems/`）是方案、总排期、归属图、系统说明页这几类的缺省位置；自己列类型的项目（`builtin_doc_types: false`）以 `doc_types` 里带对应 `role` 的条目为准（`AGENTS.md` 里列文档位置的那行也有），没有那个 role 的步骤跳过。

## 1. 五档

先问：这个改动错了，会坏到哪里？

| 档 | 什么改动 | 流程 |
|---|---|---|
| 直接改 | 注释、文档、格式、局部改名；行为不变 | 直接改，不送审 |
| 轻流程 | 只在一个模块里，调用方不受影响：修 bug、内部重构、加私有函数 | 改 → check；不单独审（`strict` 档除外） |
| 中流程 | 改了一个系统对外提供的东西，但没出这个系统：新功能、调用方都在本系统里的签名改动、新配置项 | 先写几行方案（改什么、哪些文件、怎么验证）→ 改 → 审一次代码（`off` 档除外） |
| 全套 | 碰到别的系统或持久数据：别的系统调用的接口；共享数据或它的主人；文件、存档、数据库或通信格式；系统之间的执行顺序；删除或迁移已存的数据 | 在中档之上加：方案写成文件、定好数据主人、动手前先审方案（第 2 节） |
| 系统档 | 新建或重做一整个系统；跨好几个系统的重构 | 在全套之上加：设计文档、先用原型验证风险最大的假设、用户签字、拆里程碑（第 2 节） |

拿不准往上算一档。读写了别的系统拥有的数据或时点就算全套。

**谁来做**在档位之上再加步骤：

| 执行者 | 加什么 |
|---|---|
| 自己 | 不加：没有简报、试读、派包 |
| 另一个代理 | 派包前写简报并试读（第 4 节）；交回（第 5 节） |
| 几个代理并行 | 还要：一个包一个代理，每个代理一个 git worktree；文件、时点、主人、事件都不重叠；协调者一次合入一个；`small` 项目先跑 `nomess.py init --auto --size medium` |

执行中发现方案错了，回到方案处理（第 6 节），不绕着打补丁。

## 2. 全套

1. 写方案前先看现状：谁写、谁读、在哪个时点、共享数据谁存盘；看 `<docs_root>/system-map/index.md` 上的热点清单。定好每份数据的唯一主人。
2. 写方案（第 3 节）。`<docs_root>/plans/`、`<docs_root>/schedule.md`、`<docs_root>/ownership-map.md` 和子系统页 `<docs_root>/systems/<name>.md` 第一次需要时照 `${CLAUDE_PLUGIN_ROOT}/skills/init/templates/<lang>/docs/` 里的模板建（子系统页用 `system-page.md`）。归属图还要加 docgen 项 `"owners": {"file": "<docs_root>/ownership-map.md", "builtin": "owners"}`。
3. 审方案：small 由用户看一眼；medium、large 另派一个只拿方案和归属记录的新子代理查冲突。最多两轮：第二轮只看第一轮的意见改对没有。
4. 交给别的代理做时：写简报、试读、派包（第 4 节）；它按第 5 节交回。
5. 审代码（第 7 节），再按 `merge-steps.md` 合入。

不可逆操作（删除或迁移已存数据、破坏已发布的接口）：先备份或先试跑，用户同意后再执行。

| `size` | 额外 |
|---|---|
| `small` | 没有：方案是对话里的几行；主人写进系统页的 `## 怎么用` |
| `medium` | 方案是 `<docs_root>/plans/` 里的一个文件，包列在 `## 分包` 下；包并行跑之前手工查它们的文件有没有重叠（没有脚本查这个） |
| `large` | 还要：`<docs_root>/schedule.md` 是唯一的施工入口（包、顺序、文件、状态只写在那里；文件重叠由 C4 在提交时挡）；派包前在 `<docs_root>/ownership-map.md` 里定好主人 |

**系统档**：

1. 先查成熟项目怎么做，再在 `<docs_root>/plans/` 写设计文档：目标、不做什么、子系统边界、接口、数据主人、没选的方案和理由。
2. 风险最大的假设先做原型验证；验证结论写进设计。
3. 审设计：先由新子代理审（最多两轮），再由用户签字。签字前不写正式代码。
4. 拆成里程碑，每个有验收条件；里程碑内部的活按全套或中档走。
5. 每个里程碑做完，对着设计审它合起来的改动；现实和设计对不上时，先改设计（第 6 节）。

## 3. 方案

从 `${CLAUDE_PLUGIN_ROOT}/skills/init/templates/<lang>/plan.md` 拷。

- 做完所有决定：便宜的模型读完方案和简报不用问就能开工。执行者自己拿主意是打补丁的起点。
- 只给一个主方案，不写"可以 A 或 B"；每个取舍一行理由；要有一节"没选什么、为什么"。
- **方案头**：`状态:`（提案 / 已采纳 / 已否决 / 已被取代）、`日期:`，可选 `系统:`、`取代:`、`被取代:`（写了它，状态就是已被取代）。字段名跟着 `lang` 走。
- **归档**：做完、被否决、被取代的方案挪进 `<docs_root>/plans/archive/YYYY-MM-DD-<name>.md`，不删；做完的改为已采纳。不用连续编号：并行的代理会抢同一个号。

## 4. 简报与试读

`brief-template.md` 的七段都要写。只抄方案里这个包的部分；每个文件:行都亲自核对，并注明提交；验收条件分成**测试**（从代码难推对、又容易回退的边界行为）和**读代码确认**。

**派包前试读**：把方案路径（small：方案正文）和简报交给 `nomess:trial-reader` 子代理。把它的问题的答案补进方案或简报，再试读一次；第二轮还有疑问就问用户。

写代码的代理不改共享文档：文档句子写在交回里。

## 5. 交回

对照 `brief-template.md` 第 7 段的三项查；缺项退回。

## 6. 计划返修

触发：简报和现实对不上；审查发现设计漏洞；测试或评测和方案前提矛盾。

- 执行者：停下交回，写清哪条前提不成立、看到了什么；绝不自己改方案或绕过去。
- 协调者：叫停受影响的包并标`返修中`（large：在总排期里；medium：在方案的分包里）；前提写在哪就在哪改（方案、总排期或归属图），不改抄本；在方案末尾加 `变更记录：<日期>，<改了什么>，<为什么>`；简报改好后改回`待派`。被叫停的包的提交不合入。
- small：改方案，重做。改得小（不影响别的包）：改方案和简报，试读改动的部分，重新派。改得大（数据主人、接口、别的包，或拿不准）：重新审方案；已合入且依赖这条前提的包，加一个返工包。同一个包第二次返工：问用户。

## 7. 审查

Read 并照 `${CLAUDE_PLUGIN_ROOT}/skills/review/SKILL.md` 做：什么级别审什么、意见怎么核实都在那里。

- 代码只审一次。按采纳的意见改完不再审，除非改动动了设计或新增了文件：那样只审这次修改，也只审一次。
- 逻辑对不对，主要靠审查判断，不靠测试：不要求执行者写简报里边界用例以外的测试。

## 8. 提交闸门与规则

git 钩子在每次提交时跑 `nomess check`，红项挡提交；绕过钩子会被挡。被红项拦下：改掉，或在顶层加一条带 `reason` 的 `allow`（一定会被审）。

新踩一次坑，先问能不能变成规则而不是文字提醒：`nomess.json` 的 `check.rules`（`forbid` / `require` / `cmd`），子系统之间的约束写进 `arch`，两份必须一致的东西做成 docgen 生成段。要判断的，由自动整理（`nomess:dream`）升成路径规则。

## 9. 文档

- 文档只放进文档类型的位置（`AGENTS.md` 的 nomess 段里那张清单；别处新建 `.md` 会被挡）。哪类都放不下：记一条标题为 `文档缺口: …` 的教训。
- 开发者文档（`CONTRIBUTING` 之类）只就地改；对外文档（`README`、`CHANGELOG`、文档网站）绝不自动改。
- 只写现在的样子：旧说法直接改掉，不追加"更新：…"。

## 10. 代理

一个代理一件事，做完就结束；里程碑之间换新代理，给一页交接。被权限拦下的不绕过、不托人代做。
